Attempt.steps is a nested list here, but becomes a separate attempt_steps table with a foreign key in storage (Fig. 3) — the API hands back a tree, Postgres stores rows.

Fig. 3

Database schema — five tables, two real chains

Direct mapping from the agreed API contract to Postgres tables. Two integer-keyed tables (app-generated data) and two string-keyed tables (content authored by Richard/Jeff) — the id type follows who creates the row. 

erDiagram
    PROBLEMS ||--o{ ATTEMPTS : "attempted in"
    ATTEMPTS ||--o{ ATTEMPT_STEPS : "contains"
    MISCONCEPTION_RULES ||--o{ HINTS : "explained by"

    PROBLEMS {
        bigint id PK
        text topic
        integer difficulty
        text question_text
        text correct_answer
        text solving_tip "nullable, new field"
    }
    ATTEMPTS {
        bigint id PK
        bigint problem_id FK
        text student_id
        text status "value list open"
    }
    ATTEMPT_STEPS {
        bigint id PK
        bigint attempt_id FK
        text recognized_latex
        boolean is_correct
    }
    MISCONCEPTION_RULES {
        text id PK
        text topic
        text description
        text matching_rule "format open"
        text escalation_hint_id "no enforced FK"
    }
    HINTS {
        text id PK
        text misconception_id FK
        text text
        integer level
    }
misconception_rules.escalation_hint_id points at a hint, but isn't an enforced foreign key — enforcing both directions between misconceptions and hints creates an insert-order cycle for no real benefit at seed-data scale.
Three fields are intentionally loose (text, not an enum/CHECK) pending open questions in the contract: status's value list, matching_rule's format, and difficulty's scale.

Fig. 4

Decision logic — the part that makes it a tutor

Fig. 1 shows the service calls; this is what actually happens inside them — the branching rules across the Evaluator (#25-28), Misconception Detector (#29-31), and Hint Service (#33-35). This is the one diagram that isn't just structure — it's the product's actual pedagogical logic. 

flowchart TD
    A[Step submitted] --> B{Expression valid?}
    B -- no --> C[Return invalid, ask to rewrite]
    B -- yes --> D{Mathematically correct?}
    D -- yes --> E{Legal step from the previous one?}
    E -- yes --> F[Return correct]
    E -- no --> G[Return needs review, not silently wrong]
    D -- no --> H{Matches a known misconception?}
    H -- yes --> I[Look up hint for that misconception]
    I --> J{Same misconception as last attempt?}
    J -- yes --> K[Show escalated hint, level 2]
    J -- no --> L[Show first hint, level 1]
    H -- no --> M[Show generic fallback hint]
The "same misconception as last attempt" branch (hint escalation) isn't specced anywhere yet — #34/#35 describe the two hint levels, but nothing currently defines what tracks "this is the second time" across attempts. Worth a real ticket, not just this diagram's assumption.

Fig. 5

Attempt lifecycle — including what's inside each step

The contract flags Attempt.status as "needs a fixed list." The inner states here aren't invented — they're the actual states StepBox.js already cycles through today (drawing, recognizing, confirmed, evaluated), nested inside the attempt-level state that's still just a proposal. 

stateDiagram-v2
    [*] --> in_progress: POST slash attempts creates the row

    state in_progress {
        [*] --> step_empty
        step_empty --> step_drawing: student starts drawing
        step_drawing --> step_recognizing: clicks Recognise
        step_recognizing --> step_confirmed: recognize returns latex
        step_recognizing --> step_drawing: recognition fails, retry
        step_confirmed --> step_confirmed: Edit changes the value
        step_confirmed --> step_evaluated: Check my working
        step_evaluated --> step_correct: valid
        step_evaluated --> step_incorrect: invalid
        step_incorrect --> step_confirmed: student edits and rechecks
        step_correct --> [*]
    }

    in_progress --> completed: trigger not yet defined
    completed --> [*]
The inner cycle matches what's already implemented: StepBox.js's draw/edit/recognize states, and the fact that an incorrect step loops back to confirmed rather than dead-ending — a student can keep revising one step.
Real gap found while building this: neither the API contract nor the current frontend (#43, "Check my working") defines what actually flips an attempt to completed. Checking steps isn't the same as closing the attempt — this needs a decision before #12/#15 land, not just a status column.
